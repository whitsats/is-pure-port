# 0x17、章节标题与快速存档的核查（2026-11-15）

## 2026-11-15 真实新游戏路径（本轮）

本轮新增 `转换器/mac_new_game.py` 与 `emit_webgal.py --new-game`，从
`MAC_000.bin:0x0C` 使用零初值状态执行，不加载任何即时存档。产物：

- `数据/真实新游戏_0x0C至0x2344.txt(.json)`
- `数据/真实新游戏场景/`、`数据/真实新游戏语音/`
- `真实新游戏样片/public/`

实际轨迹为：`MAC_000:0x78 reg_calc 0x17(0)` → `0x80 quick_save` →
`0x84 title_disp`（`intro:杂志彩页上的少女;`）→ 开头 74 句 →
`0x73C ext_goto` → `MAC_001:0x0C` → `0x58 reg_calc 0x17(1)` →
`0x60 quick_save` → `0x64 title_disp`（`intro:Ｉ´Ｓ・小队結成;`）→
`0x2118 vib_set` → `0x2344` 的 `伊织的手堵住了我的嘴巴。`。报告共 411 条
`sources`（74 + 337 条对白），停止于 `MAC_001:0x2344` 且包含该条指令；
`title_disp` 记录偏移分别是 `0x000AE8`、`0x000AF4`。这不是从存档拼接的快照：
`initial_state` 明写状态块按 memset 清零、位表为零、未使用任何即时存档。

**2026-11-15 运行期复核（已更正）：** 上面的零位表就是**新游戏的实际初值**，不是仅凭 BSS 的保守假设。两组运行期读数必须分开看：

- A 组（用户原配置，Slot 1 = 全分支通关卡 `ispure-complete.ps2`）：PINE `127.0.0.1:28011` 读到 `0xB1EC20=57`、`0xA98C50` 前 8 字节 `ffffffffffffff01`（57 位全 1）、到目标时 `G+0x440=1`、`G+0x4B0=1`，两次 `0x17` 都进 `0x1174B8(3)`，场景表 1 项且 `u16@+8=0`（非类型 3），未新增标志。这些是**全通关进度态**。
- B 组（独立 PCSX2 副本 + 空白未格式化卡副本，PINE `28012`）：标题态 `state=0` 时计数 57、位表全 0；`MAC_000:0x78 0x17(0)` 后 `01`、`G+0x440/+0x4B0=0/0`；一次 L 输入使 `MAC_001:0x58 0x17(1)` 前 `01`（`0/0`，`0x6D4`）变为后 `03`（`1/0`，`0x74`）。这些是**新游戏初态**。

所以转换器的零位表与 `0x4B0=0/0` 与新游戏一致，不需要改成全置位初始化；全 1 应作为“全通关参照”单独保存。详细数值、状态与截图见 `数据/运行期取证/隔离空白卡_新游戏初值.json`（B 组）与 `PINE取证_0xB1EC20.json`（A 组，已标注全通关背景），以及 `PCSX2_目标对白_slot26.p2s`、`验证/真实新游戏_PCSX2_目标对白.png`。B 组的采样是按键粒度前后批量读取，不是 CPU 取指级原子快照。

**运行期分支重算：** 计数 57 在两种状态下都是运行期实读值（它是标志总数，不随进度变化）。新游戏（空白卡）位表两次 `0x17` 前都为 0、`G+0x4B0` 为 `0/0`，不满足“全部相关位为 1”，因此**不调用** `0x1174B8(3)`；转换器的零模型与此一致。全通关卡上位表全 1、`0x4B0` 为 `1/1`，两次都调用 `0x1174B8(3)`，但场景表唯一项类型为 0，故 `scene_flags` 也没有新增类型 3 索引。

**纠错边界：** `0x1042B0` 不在 `MAC_000:0x0C` 的脚本指令流中，本次转换器也没有把它当成新游戏批量初始化的执行步骤。它由原生代码在别的状态调用（例如 `0x141FB4`），此前把它写成“新游戏必然读取状态位 `0x10/0x11/0x12` 并批量置位”的说法没有作为本路径的证据使用；新游戏位表为零的直接依据是 BSS/零填充区、未执行该原生调用，以及空白卡隔离冷启动的 `state=0` 实测（全 0）。全通关卡与即时存档的 57 位全为 1 只是那些状态，不能反推新游戏。

### `vib_set` 依赖与本轮状态写入

`MAC_001:0x2118` 的原始字节是 `57 10 06 04 05 01 00 00`。`0x0011EF80` 读取
`ip[1..5]`，写 `G+0x299..+0x29D` 为 `16,6,4,5,1`；随后调用的
`0x0013ED30` 清零 `G+0x28C/+0x290/+0x294`。报告 `displays` 保存了这条
`vib_set`、全部状态写入和“硬件振动未映射”的原因。它不读取 `0xA98C50`
位表，也没有因 `0x17` 的状态缺失而停住；转换器执行它而不是跳过。

### 循环、graph_pos 与 quick_save

- `MAC_001:0x21D0` 到 `0x230C` 是一个会重复到达同一偏移的有限循环（本轮观察到
  17 次 `graph_pos`/`time_wait`）。转换器只在“同一偏移且状态完全不变”时判环；
  状态随循环变化时允许继续，最终条件变为不跳转并走到 `0x2344`。这不是无条件
  放开跳转。
- `graph_pos` 的 72 条记录只写入 `displays`，不生成画面命令；它们不改变剧情状态。
- 两次 `quick_save`（`0x80`、`0x60`）只记录进程内检查点并继续；没有伪造记忆卡，
  也没有声称已经实现 `0x1161C0/0x116AD0` 的内部复制。该限制写在报告和交接中。

## 已证实的修正

此前对 `reg_calc 0x17` 的静态分析有三处错误：MIPS `jal` 的延迟槽先执行，将指令编号写入 `G+0x440`；返回的旧位值写入 `G+0x4B0`；读取和置位使用同一位表 `0xA98C50`，并且**全部相关位为 1** 时才继续处理场景类型表。以此处及 `数据/reg_calc17ELF证据_修正.json` 为准。

`转换器/校验reg17指令执行.py` 将用户已有 PCSX2 即时存档中的 EE 内存复制到隔离的 Unicorn 中，以与 ELF 一致的原始 MIPS 指令运行，并与 Python 状态模型的全部相关写入比较。真实快照加两种构造状态共三例通过；另有 13 个状态读写对照通过。构造状态只是验证不同分支的输入，不代表用户曾玩到这些状态。

即时存档 SHA-256 为 `ec33990c479a82bd7985bf17eb28b501c091805d91e90e389fdc412086269297`。画面位于开场附近，但存档中 57 个相关位已全部为 1，不能视为新游戏初始状态。整个过程只读取存档，所有状态修改都在内存副本中进行。

转换器现支持显式 `--state-snapshot` 研究模式；没有快照、也没有 `--new-game` 时仍拒绝未经初值确认的 0x17。`--new-game` 则使用本轮记录的零初值和 `NewGameRuntime`，不是快照模式。用已有存档的状态假设从开头推进，已到 `MAC_001:0x60 quick_save`，但这不是原游戏实际连续运行录像。详细报告与复现实验见 `数据/reg17指令执行对照.json`、`数据/快照状态读写指令对照.json`、`数据/快照轨迹_MAC000至MAC001.txt.json`。

## 章节标题

`title_disp` 的 `0x11E7E4` 起读取 `G+0x440` 作为 12 字节标题记录下标，读取 `G+0x4B0` 并加 6 后作为显示函数参数；记录中 `+4` 的指针传入文字显示函数。静态 INIT 的 57 条标题已提取并接入 `intro`，相邻的 52 **不是**标题表长度；原版与 v7.4 的 0x8145/0x8140 作为显式证据替换处理。详见 [`章节标题`](章节标题.md)。这些记录仍不等于完整还原标题演出、时序或字体。

## quick_save

处理函数 `0x11D888` 会根据 `G+0x4C5` 决定是否调用 `0x1161C0`，并根据指令参数 1/2 和 `0xA98DA3` 的对应位决定是否调用 `0x116AD0`；最后将脚本指针推进 4 字节并调用 `0x117DC0`。`转换器/校验quick_save分派.py` 在隔离环境执行原处理函数，覆盖参数 0–3、开关 0/1 和低两位四种组合，共 32 组匹配 `数据/quick_save分派指令对照.json`。

上述试验把三个被调函数替换为立即返回的桩，只验证分派条件及指令长度；不验证其内部行为。`0x1161C0` 至少复制/合并状态数据，`0x116AD0` 存在较大范围内存操作及系统调用，不能简单跳过或等同 WebGAL 一次快速保存。WebGAL 的自动保存可用于安卓样机，但尚未证明覆盖原游戏全局解锁和状态复制的语义。

本轮 `--new-game` 的 `NewGameRuntime.apply_quick_save` 只记录两次进程内检查点（`MAC_000:0x80`、`MAC_001:0x60`）并继续，不写入记忆卡、不调用原生 `0x1161C0/0x116AD0`。这是“让新游戏路径不被存档内部复制挡住”的最小处理；原版存档的完整语义仍未实现，报告中的 `quick_save_checkpoint` 不应被解读为等价存档。

在已有快照的内存副本中单独执行 `0x1161C0`，观察到对四个范围共 560 字节的写入；该快照写入前后数据恰好一致。继续独立执行 `0x116AD0` 时，在异常前记录到 72,500 次写入、49,213 个涉及字节，其中 2,056 个字节不同；Unicorn 在 `0x116D1C` 附近发生 CPU 异常，函数没有正常返回，记录见 `数据/quick_save辅助函数_模拟系统调用.json`。这次没有到达预设的系统调用替身，结果仅代表执行到异常前的部分行为，不能作为完整存档实现或真实读写证据。

## 2026-11-15 PCSX2 冷启动实测与 PINE 读取

更新 `PCSX2/inis/PCSX2.ini` 的 `[EmuCore] EnablePINE = true` 后启动 PCSX2 v2.8.2，
`netstat` 确认 `127.0.0.1:28011` 监听；用 PINE 的 `MsgRead32` 读取，不依赖 GUI。
冷启动使用 `game-original.iso`（`SLPM-66570`，CRC `7C3CD179`，现有记忆卡），未加载任何即时
存档；从标题进入新游戏，用 Circle（键盘 L）推进。到目标时 PINE 读取并保存
`数据/运行期取证/PCSX2_目标对白_slot26.p2s`，截图原文：

> 伊織ちゃんの手がオレの口を塞いでいる。

对应汉化文本“伊织的手堵住了我的嘴巴。”，停止偏移 `MAC_001:0x2344`。截图见
`验证/真实新游戏_PCSX2_目标对白.png`。PINE 数值、状态 SHA-256 和分支记录在
`数据/运行期取证/PINE取证_0xB1EC20.json`，首个对白状态在
`数据/运行期取证/PCSX2_首个对白_slot06.p2s`。

复现要点：

```bash
# 1. 在 PCSX2 的 ini 中设置 EnablePINE=true，启动游戏后确认端口
netstat -ano | findstr 28011
# 2. PINE: u32 total_len + 0x02 + u32 address
#    total_len 含自身 4 字节；返回 4 字节长度 + 结果字节 + 4 字节值
#    例：读取 0xB1EC20 -> 57
```

取证结束后已恢复用户原始 `PCSX2/inis/PCSX2.ini`（`EnablePINE = false`），并删除
本次生成的 `SLPM-66570 (7C3CD179).*.p2s`；用户的
`SLPM-66570 (B2D68920).01.p2s` 未被覆盖。
