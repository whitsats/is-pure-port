# 为什么 `0x1EC` 三版都对不上，以及它到底写了什么

`MAC_000.bin` 开头在 `0x1EC` 的 `msg_disp2` 停下，报告理由是“中文未唯一匹配或缺失”。
本文件把这条理由查到底：磁盘上那个槽位的实际字节、三份候选各自卡在哪、以及有没有可逐字节核对的中文。

复现命令（只读，不改归档）：

```powershell
cd 'E:\Entertainment\IS\移植验证\WebGAL移植'
python -B 转换器/核查字码表缺口.py --output 数据/字码缺口核查.json --codes-output 数据/字码补充推断.json
```

## 1. 这条台词的坐标

| 项 | 值 |
| --- | --- |
| 指令 | `MAC_000.bin` `0x1EC` `msg_disp2`（`600000002b0c000013000c00`） |
| 文本偏移 | `0x0C2B`（脚本内偏移） |
| 行号 / 语音 | 19 / 12（`VOICE_00012`，已校验） |
| 原盘日文 | `寺谷「オオオッ、イヤがっていたわりにはノリノリじゃねえーか」`（cp932 60 字节） |

槽位长度 = 原盘日文的字节数 60，汉化盘把中文写进这 60 字节，不足补 `0xFF`，控制符位置不动。

## 2. 三个版本的盘上的实际字节

用 `MAC_解析.py` 从各来源解出 `MAC_000` 并取 `0x0C2B` 起的 60 字节：

| 来源 | 结果 |
| --- | --- |
| `game-original.iso`（原盘） | 就是上面那句日文（cp932 解出完全一致） |
| `game-v7.4.iso` | `88 b9 88 ba 81 75 8c a9 8c a9 8c a9 96 43 96 43 8a 66 …` |
| `一键打盘/patch/mac-v6.afs` | 与 `game-v7.4.iso` 的 `MAC_000` **逐字节相同**（sha256 前 16 位 `9213bce33f3bec8d`） |
| `输出-保护边修复/MAC/MAC_000.bin` | 与原盘相同（`569873d5bda110d0`）——转换器读的是**日文原盘**脚本 |

用作者码表（`D:\Code\IS汉化\原始解包\输出码表.txt`，3126 字）反向解码汉化盘那 60 字节，得到：

```
寺谷「噢噢噢<9643><9643>嘴上说着不情愿，拍起来这不是挺放得开的嘛！」
```

即：**汉化盘写入的正是 v7.4 译文**，只是其中两个 `—` 用的是 `0x9643`。

## 3. 三份候选各自卡在哪

| 候选 | 文本 | 判定 | 原因 |
| --- | --- | --- | --- |
| v7.4 工程 | `寺谷「噢噢噢——嘴上说着不情愿，拍起来这不是挺放得开的嘛！」` | `字码缺失` | `—`（U+2014）不在作者码表里，`校验实际汉化盘.py` 无法把它编码成字节，比对在第一个 `—` 处就退出 |
| 汇总表 | 同上（这一行与 v7.4 完全相同） | `字码缺失` | 同上 |
| v7 工程 | `寺谷「哦哦哦，表面一副厌恶的样子其实看到这些不也兴致勃勃么」` | `不一致` | 能编码，但盘上写的是 v7.4 文本，与 v7 文本不同——这是**版本差异**，不是错误 |

所以“三版都对不上”是两件不同的事：v7.4 / 汇总被**码表缺口**卡住（根本没比到字节），v7 是**文本确实不同**。
盘上没有任何一条“第四种文本”。

## 4. 那个缺失的字码

全盘扫（9,753 条可关联地址的台词，逐槽位反向解码并与 v7.4 候选逐字符对齐）只发现**两个**作者码表里没有的字码：

| 字码 | 对齐到的字 | 支撑行数 | 冲突 |
| --- | --- | --- | --- |
| `0x8140` | `　`（U+3000 全角空格） | 226 | 无 |
| `0x9643` | `—`（U+2014 破折号） | 308 | 无 |

“支撑”指：该字码出现在槽位里，按字符位置对齐到候选译文的同一个字；308 行全部对到 `—`，没有一行对到别的字。
数据在 `数据/字码缺口核查.json`（含每行状态与例子）与 `数据/字码补充推断.json`（紧凑的补充字码，含 support）。

**这不是已证实的作者码表**：字体的字模没有核对，这里只有“磁盘字节 ↔ 候选文本”的对齐证据。
按项目惯例，它被单独标成“对齐推断（字体字模未核对）”，只在 `--extra-codes` 显式传入时参与对盘。

## 5. 结论：这一句有没有可逐字节核对的中文？

有。前提是接受上面那一条对齐推断 `0x9643 = —`：

- 把 v7.4 文本按“作者码表 + 补充字码”编码，得到的 60 字节与 `game-v7.4.iso` / `mac-v6.afs` 的槽位**完全相等**；
- 于是 `数据/三版译文与汉化盘核查_补字码.tsv` 里这一行变成 `v7.4工程文本对盘 = 逐字节一致`；
- 转换器用这张表后，`MAC_000` 开头**继续往下走 4 句**（`0x1EC`、`0x1F8`、`0x204`、`0x210`），
  停在 `0x21C` 的 `file_read`（`0f000050`，“未转换的指令”）。

如果要求更严格（不接受对齐推断），那就只能由人工或字体核对确认 `0x9643` 的字模；在那之前这一行保持“缺译”状态，
转换器用严格表时仍停在 `0x1EC`——两条路径都保留在仓库里，没有二选一地删掉证据。

## 6. 边界与遗留

- 没有改 `一键打盘/patch/mac-v6.afs`、`game-v7.4.iso`，也没有改历史核查表 `数据/三版译文与汉化盘核查.tsv`；
  新增的是 `_补字码` 变体和补充推断 JSON，来源记录在 `数据/三版译文核查来源_补字码.json`。
- 补充字码只用于**对盘核对**，不会被写回作者码表，也不会用于合成新译文。
- 仍未核对：`0x9643` 的字模形状（需要字体图集，属于 `字体研究/` 的范围）；
  `0x8140` 同样只是对齐推断。
- 下一个真实阻塞变成 `0x21C` 的 `file_read`：它是 SE/语音文件读取类指令，语义尚未从 ELF 追出。

## 7. 后续（2026-11-14）

选译规则已改为**只按剧本与指令偏移取 v7.4 原始工程的最终译文**，盘面是否逐字节一致不再决定选哪一版。因此即使不接受 `0x9643` 的字码推断，`0x1EC` 也不会再阻断：`MAC_000` 开头随后又越过 SE 与淡入淡出，现在 74 句，停在 `0x730` 的 `time_wait`。本文的磁盘逐字节结论继续作为独立证据保留；历史核查表未改写。
