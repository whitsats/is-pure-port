# SE 段（`0x224`–`0x357`）解码、音频未映射的原因与新卡点

本文接着 [`文件读取与SE阻塞.md`](文件读取与SE阻塞.md)：那里证明了 `0x21C` 的 `file_read` 是空操作，
本轮把紧随其后的三段 SE 全部按字节解出、写进产物（记 `se_events`），但**不映射音频**，
转换因此推进到 `0x358` 的 `fade_start`。全部地址与统计都可由文末命令复现，
ELF 侧产物是 `数据/SE段ELF证据.json`（`转换器/SE段证据.py` 生成）。

**后续（同日）：** `fade_start`/`fade_wait` 与随后的 `se_del` 已解码并记账；
随后 `0x730` 的 `time_wait` 生成 `wait:2000;`，`0x73C` 的 `ext_goto` 跟进 `MAC_001.bin 0x0C`，
新停止点是 `MAC_001.bin 0x58` 的 `reg_calc 0x17`。见
[`淡入淡出与se_del.md`](淡入淡出与se_del.md) 与 [`等待与跨剧本跳转.md`](等待与跨剧本跳转.md)。
本文的 38 句产物保留为 SE 阶段的证据。

## 结论摘要

- `MAC_000` 开头里的 SE 出现三次（`0x224`、`0x260`、`0x318`），三段**形态完全相同**：
  `se_speed(通道 0, 1)` → `se_vol(通道 0, 0x80)` → `se_set(通道 0 ← staging 样本号)` →
  `se_req(通道 0, 2)` → `se_wait(通道 0, 1)`。前两段之前各有 `file_read 0x5000` / `0x5003`，
  第三段之前是 `file_read 0x5001`。
- 全盘 74 个剧本共 **13,618** 条 SE 指令，其中这种“五连块”出现 **2,187** 次；`se_req` 参数 `2`
  恰好 **2,321** 次，与 `file_read` 的 2,321 条一一对应。这是固定形态，不是单条偶然。
- **音频不映射**：`se_set` 用的两张表（`*(0xB1EC00+0x88)` 字节表、`*(0xB1EC00+0x6B90)` u16 表）
  是运行时装载模块内的相对偏移，被 `0x103AD4` / `0x103C20` 加上装载基址后写进全局结构；
  表里只有“12 位编号 → 状态字节 / 句柄”，**没有文件名**，`0x1173E8` 也不接触文件名。
  “编号 0–151 → `se.afs` 条目”无法静态证明，所以产物中**不存在任何** `playEffect`
  或音频路径，只有记录。
- `se_wait` 在原程序会阻塞；移植版不等待（明确记在 `se_events` 的 `webgal.reason` 里），
  代价是每段 SE 少一个音效时长——本轮样片共 3 段。

## 2. 五条 SE 指令的操作数与写入位置

通道结构基址 = `*(gp-0x6D44) + 0x3F480 + 通道号*12`（`0x0012D3F0` 一带与 `0x11D1C0`
的 `lui $at,4` + `-0xb78` 相减可互证；`数据/SE段ELF证据.json` 的 `channel` 字段）。

| 指令 | 处理函数 | 读什么 | 写什么 | 证实程度 |
|---|---|---|---|---|
| `se_speed` `0x3E` | `0x0011D188` | `lbu ip[1]`=`0x0011D19C`，`lhu ip[2]`=`0x0011D1A4` | `通道+8` u16 = 速度（`0x0011D1C8`） | 完整 |
| `se_vol` `0x3F` | `0x0011D1E0` | `lbu ip[1]`=`0x0011D200`，`lbu ip[2]`=`0x0011D22C` | `+2 → +3`（`0x0011D218`/`0x0011D21C`），新音量写 `+2` | 完整 |
| `se_set` `0x3A` | `0x0011D080` → `0x0012D3D0` | `lbu ip[1]`=`0x0011D0B8`；样本号 = `ctx+0xD51FA`（`0x0011D0B0`，即上一条 `file_read` 的 code） | `通道+0` u16 = 样本号（`0x0012D40C`）；随后 `0x107CB8(0x281580+通道)`、查两张表、`仅当状态字节==2 且句柄≠0xFFFF` 时 `j 0x1173E8`（`0x0012D45C`） | 写入完整；**是否起播取决于运行时状态字节** |
| `se_req` `0x3C` | `0x0011D138` → `0x0012D4A0` | `lbu ip[1]`；`u16@2` 的低字节 `0x0012D4C0` | `通道+5` = 参数低字节；`通道+6` = 0（`0x0012D4D0`） | 写入完整；参数语义（2/3/4）未证实 |
| `se_wait` `0x3D` | `0x0011CC18` | `u16@2`=`0x0011CC34`；参数 1 走 `0x0011CC48`→`0x0011CD28` | 不满足时清 `ctx+0xD` 且不前进（`0x0011CDFC`） | 阻塞行为完整，终止条件依赖通道状态 |

## 4. 两张表的来源，以及为什么不能把编号映射成音频

`se_set` 的起播判断读两处：

```
0x0012D43C  lw  $v0, 0x6b90($a2)     ; *(0xB1EC00+0x6B90) = u16 句柄表
0x0012D440  addu $v0, $a1, $v0       ; a1 = (样本号)*2
0x0012D444  lhu $v1, ($v0)
0x0012D428  lw  $v0, 0x88($a2)       ; *(0xB1EC00+0x88) = 字节状态表
0x0012D42C  addu $v0, $v0, $s0       ; s0 = 样本号
0x0012D430  lb  $v1, ($v0)
```

两个指针都不是静态数据：

- `0x00103AD4`：`sw $v1, 0x88($a2)`，其中 `v1 = *(s1+0x40) + s1`；
- `0x00103C20`：`sw $a1, 0x6b90($v1)`，其中 `a1 = *(s1+0x74) + s1`；
- 装载：启动流程 `0x00108C18` 调 `0x101468(a0 = 8, a1 = "init.bin", a2 = 0x00A54700,
  a3 = 0x00D72980)`，随后 `0x00108C24` 调 `0x1035D8(0x00A54700)` 做整套指针重定位。

即：两张表是**运行时装载模块内的数组**，`s1` 是装载基址；表项是“状态字节 / 句柄”。
`se_set` 起播走 `0x1173E8`，后者只调用 `0x1053C0` 并遍历一张 0x10 字节记录表
（`0xB1EC00+0x68C4` 计数、`+0x68C8` 项数），同样不接触任何文件名。

所以：

- `se.afs` 确实存在（卷表 `0x212E00` 起每行 `0x20` 字节，`0x212EE0` 行 `+0x00` = `5`、
  `+0x18` 指向 `se.afs`、`+0x1C` = `0x45C980`；ISO 上 174 条 CRI ADX）；
- 剧本里的编号 0–151 落在 174 条之内，但这只是**相容**；
- 没有任何静态字符串、表项或指针把“编号 n”与 `se.afs` 第 n 条连起来。

因此本轮**不导出、不引用**任何 SE 音频：产物里只有 `se_events` 的字节与操作数记录，
`webgal.mapped` 全为 `false`，没有任何播放命令，也没有任何音频路径。

## 5. `se_wait` 与原版的差异

原程序 `0x0011CC18` 在通道状态未满足条件时清 `ctx+0xD` 且**不前进**（VM 下一帧重跑同一指令），
也就是会等到该音效结束。移植版不等待：`se_events` 里 `blocks_in_original: true`、
`waited: false`，`webgal.reason` 写明“音频未映射，所以不阻塞，节奏会比原版短一个音效时长”。
本轮样片里这样的地方有 3 处（`0x234`、`0x270`、`0x328`）。

## 6. 当时的卡点：`0x358` `fade_start`（现已解码）

```
0x358  68 80 1e 00 ff 0f 00 00
```

命令表里 `0x68` 是 `fade_start`，长度 8 字节，处理函数 `0x0011E398`。本轮没有解码它的参数
（`ip[1]=0x80`、`u16@2=0x1E00`、`u32@4=0x00000FFF` 的含义未核实），因此停在这里。
这是当时下一条真正未解码的指令，不再是 SE。后续已解出方向位、时长、颜色与等待条件，
见 [`淡入淡出与se_del.md`](淡入淡出与se_del.md)。
