# `file_read`（`0x0F`）的语义与 `0x21C` 之后的第一处阻塞

本文只写能从 `输出-保护边修复/SYSTEM/SLPM_665.70` 与本盘字节直接读出的事实。
复现命令见文末；现场反汇编产物是 `数据/文件读取ELF证据.json`
（由 `转换器/文件读取证据.py` 生成，所有地址都是脚本现读的）。

**后续（2026-11-14）：** `time_wait` 与 `ext_goto` 已接入；抬头产物已越过 `0x730`，
在 `0x73C` 跳到 `MAC_001.bin 0x0C`，停在 `MAC_001.bin 0x58` 的 `reg_calc 0x17`。
本文关于 `file_read`/SE 的结论不变；新停止点见 [`等待与跨剧本跳转.md`](等待与跨剧本跳转.md)。

## 一句话结论

`0x21C` 的 `file_read`（`0f000050`）**不是**“去磁盘读一个文件”。它把
`(style = ip[1] = 0, code = u16@2 = 0x5000)` 交给 `0x12D980`；`style 0` 才会进
`0x12D810`，而 `0x12D810` 按 `code >> 12 = 5` 查跳表 `0x259FD0`，组 5 落在
`0x12D8B8` —— 那里只有 `a2 = 0`，紧接着 `beql $a2,$zero → 0x12D970` 直接返回。
**不拼文件名、不调用任何读取接口**，随后只把这三个值写进 staging 槽位并让 `ip += 4`。
紧随的 `file_wait`（`0x220`）轮询该槽位、立即完成。

因此这条指令可以按“记账”实现而不产生任何输出；转换器已经这么做，`MAC_000` 开头
**越过 `0x21C` 与 `0x220`，停到 `0x224` 的 `se_speed`**。句子数仍是 23 句，
因为下一条 `msg_disp2` 在 `0x238` —— 中间隔着 `0x224`–`0x234` 整段 SE 指令，
那段没有实现（原因见第 7 节），所以本轮没有新增台词，也没有把 SE 段当成已完成。

## 1. 分派：用命令表的哪一个字段

命令表在 `0x213590`，条目 24 字节，字段顺序是
`handler, name, ?, mode1, mode2, length`（`数据/命令表.tsv` 同一份来源）。
全 ELF 只有两处按这张表取址：

| 位置 | 指令 | 作用 |
|---|---|---|
| `0x00117B0C` | `addiu $at, $at, 0x3590` | 由 `lbu ($t0)` 取操作码、`opcode*24` 定位条目 |
| `0x00117DFC` | `addiu $at, $at, 0x3590` | 同上，随后 `0x00117E04` 的 `lw $v1, ($v0)` 取**第一字段** |

`0x00117DC0` 把第一字段写进 `ctx+0`，`0x00117DE4` 同时置 `ctx+0xD = 1`。
所以真正执行的是 `handler`：`0x0F → 0x00119878`，`0x10 → 0x001198E0`。
表里的 `mode1`（`0x0F` 是 `0x1183C0`）没有任何分派路径引用它——这一点对结论不影响：
`0x1183C0` 对 `ip[1] == 0 且 code>>12 != 0` 的分支同样是“只写 staging、`ip += 4`、
不发起读取”（`0x00118418`–`0x00118428`），两条路径对本条指令的可观察结果一致。

## 2. 操作数形态

`0x00119878` 的前几条：

```
0x00119888  lw  $v0, 0x44($s0)      ; ctx->ip
0x0011988C  lw  $v1, 8($v0)         ; ip
0x00119890  lbu $a0, 1($v1)         ; a0 = ip[1]   ← style
0x00119894  jal 0x12d980
0x00119898  lhu $a1, 2($v1)         ; a1 = u16@2  ← code（延迟槽）
0x0011989C  bnez $v0, 0x1198c0      ; 非 0 → 不前进
0x001198AC  addiu $v0, $v0, 4       ; 返回 0 → ip += 4
```

即 `ip[2]` 是低字节、`ip[3]` 是高字节：`0f 00 00 50` → `style=0`、`code=0x5000`。
`ip[3]` 在全盘恒为 `0x50`（见第 5 节），所以 `code` 总是 `0x5000 + 序号`。

## 3. 执行路径（逐地址）

`0x0012D980(style, code)`：

```
0x0012D998  beq  $s0, 1, 0x12d9e0   ; style==1 → v1 = 0（不调用任何东西）
0x0012D9A4  beql $v0, $zero, 0x12d9c0  ; style>=2 → v1 = 0
0x0012D9AC  beqz $s0, 0x12d9d0      ; style==0 → 调用 0x12D810
0x0012D9D0  jal  0x12d810           ; a0 = code & 0xffff
0x0012D9E4  bnel $v1, $zero, 0x12da20   ; 0x12D810 返回非 0 → 返回 1（重试）
0x0012D9FC  sb   $a0, 0x51f8($at)   ; 挂起 = 1
0x0012DA0C  sb   $s0, 0x51f9($at)   ; style
0x0012DA18  sh   $s1, 0x51fa($at)   ; code
```

失败/未完成时的降级：`0x12D980` 返回非 0 时，`0x0011989C` 的 `bnez $v0` 走 `0x001198C0`–`0x001198C8`
——把 `ctx+0xD` 与 `ctx+0xE`（均为 u8/u16 字段）清 0、`ip` **不前进**，由 VM 下一帧重新执行
同一条指令；返回 0 才是“完成”。组 5 因为没有描述表，`0x12D810` 总是返回 0，
所以不会走到这个重试分支。

`0x0012D810(code)`：

```
0x0012D81C  srl  $s0, $a0, 0xc      ; group = code >> 12   （本例 5）
0x0012D820  andi $a1, $a0, 0xfff    ; index = code & 0xFFF （本例 0）
0x0012D824  sltiu $v0, $s0, 8
0x0012D844  lw   $v1, -0x6030($v1)  ; 跳表 0x259FD0 + group*4
0x0012D848  jr   $v1
```

跳表实测（`ev.table_at(..., 0x259FD0, 8)`）：

| group | 目标 | 说明 |
|---|---|---|
| 0 | `0x12D850` | 描述表 `*(0xB1EC4C)`，索引不乘 2 |
| 1 | `0x12D860` | 描述表 `0xB1EC54`，索引×2 |
| 2 | `0x12D878` | 描述表 `0xB1EC5C`，索引×2 |
| 3 | `0x12D890` | 描述表 `0xB1EC64`，索引×2 |
| 4 | `0x12D8A8` | 描述表 `0xB1EC6C` |
| **5** | **`0x12D8B8`** | `addiu $s0,$zero,5` / `move $a2,$zero` → `a2 == 0` |
| 6 | `0x12D878` | 复用组 2 |
| 7 | `0x12D860` | 复用组 1 |

组 5 之后：

```
0x0012D8C0  beql $a2, $zero, 0x12d970   ; 没有描述表就跳走
0x0012D970  move $v0, $zero             ; 返回 0
0x0012D978  jr   $ra
```

`0x12D8B8`–`0x12D8C4` 之间没有 `jal`/`jalr`/`syscall`（用例
`test_group_five_has_no_description_table` 直接断言这一点），组 0–4 才会走到
`0x0012D8F8` 一带去拼名字并调 `0x101E90`。
换句话说：**“组 5 的 file_read” 在这个 build 里是一条空操作**，只留下记账。

## 4. staging 槽位与 `file_wait`

`ctx` 基址是 `*(gp-0x6D44)`（VM 状态块，初始化 memset 0，见
`验证/状态与条件.md`）。相关字节：

| 偏移 | 写者 | 含义 |
|---|---|---|
| `+0xD51F8` | `0x0012D9FC` / 清于 `0x0012DAA4` | 挂起标志 |
| `+0xD51F9` | `0x0012DA0C` | style |
| `+0xD51FA` | `0x0012DA18` | code（`se_set` 会读它，`0x0011D0B0`） |
| `+0xD51FC` | `0x0012DAB0` | `file_wait` 取到的结果 |

`file_wait`（`0x001198E0`）转 `0x0012DA38`：

```
0x0012DA4C  lbu $v1, 0x51f8($v1)
0x0012DA50  beqz $v1, 0x12daf4     ; 没有挂起 → 返回 0（视为完成）
0x0012DA60  lbu $v1, 0x51f9($v1)   ; 按 style 分派
0x0012DA80  jal 0x101a00(-1)       ; style 0：先轮询
0x0012DA90  jal 0x101a80(-1)       ; 非 0 时取结果
0x0012DAB0  sw  $v0, 0x51fc($at)   ; 存结果
0x0012DAA4  sb  $zero, 0x51f8($at) ; 清挂起
```

对组 5，`0x12D980` 已经把挂起位置 1，所以 `file_wait` 会走一次
`0x101A00(-1)`/`0x101A80(-1)` 再清位；这两个是声音/流读取接口，参数都是 `-1`
（“任意/全部”），本条指令没有传入任何名字或编号，因此也无法据此确定任何资源。

## 5. 全盘统计：这不是单条巧合

`转换器/文件读取证据.py` 扫描 74 个 `MAC_*.bin` 的全部指令边界：

| 项 | 值 |
|---|---|
| `file_read` 条数 | 2321 |
| `code` 高字节 | 只有 `0x50` |
| `code` 取值 | `0x5000`–`0x5097`（152 种） |
| 紧跟着 `file_wait` | 2321 / 2321 |

即“`file_read 0x00 / 0x50XX` + `file_wait`”是唯一的调用形态，没有别的 style，
也没有别的 `code` 前缀。这一点写进了 `tests/test_file_read.py`：
一旦原盘或命令表变了，用例会先失败。

## 7. 为什么停在 `0x224`：SE 段已取到与仍缺

已取到（地址与结构偏移都能逐条对回反汇编）：

| 指令 | 处理函数 | 已证实的动作 |
|---|---|---|
| `se_speed` `0x3E` | `0x11D188` | 把 `u16@2` 存到通道结构 `+8`（`sh $t0, -0xb78`，基址 `0x3F480 + 通道*12`），`ip += 4` |
| `se_vol` `0x3F` | `0x11D1E0` | 旧音量 `+2 → +3`，新音量 `ip[2] → +2`，`ip += 4` |
| `se_set` `0x3A` | `0x11D080` → `0x12D3D0` | 通道号 `ip[1]`；把 staging 的 `+0xD51FA` 存进通道 `+0`；调 `0x107CB8`（按通道 `0x281580+ch` 的对象做 `0x1B7DA8(handle,0)`、`0x1B6FA0(handle)` 并清 `+3` 标志）；再按 `code & 0xFFF` 查 `*(0xB1EC00+0x88)` 的字节表与 `+0x6B90` 的 u16 表，**仅当字节表值为 2 且句柄 ≠ 0xFFFF 时** `j 0x1173E8(handle, 1)` |
| `se_req` `0x3C` | `0x11D138` → `0x12D4A0` | 通道 `+5` 写 `u8@2`（本例 2），`+6` 清 0 |
| `se_wait` `0x3D` | `0x11CC18` | 按 `u16@2` 分派；参数 1 走 `0x11CD28` 一带，读全局 `+0x47C` 与通道 `+5`，不满足就置 `ctx+0xD = 0` 不前进（即阻塞） |

仍缺（缺一条就不能称“已实现”）：

1. **`code & 0xFFF`（0–151）到 `se.afs` 条目的对应**。`se.afs` 确实存在：
   卷表 `0x212E00` 起每行 `0x20` 字节，`0x212EE0` 行的 `+0x00` 是 `5`、
   `+0x18` 指向字符串 `se.afs`、`+0x1C` 是大小 `0x45C980`；ISO 上该 AFS 有
   **174** 条 CRI ADX（`输出-保护边修复/SE/adx/SE_00000..00173`），152 种编号
   都落在 0–151 < 174 之内。但“相容”不是“相等”：没有证据表明 `se.afs` 的
   第 n 条就是编号 n，也没有证据表明中间没有一张重排表。
2. **`0xB1EC00+0x88` 的字节表与 `+0x6B90` 的 u16 句柄表是谁填的**。两处都是
   BSS 指针，写者是 `0x103B40` 一带的“装载 + 指针重定位”代码（`s1` 是装载基址，
   `0x00103C20` 把 `0x6B90` 写成 `偏移 + s1`）。对应哪个文件、以什么顺序填
   ​152/174 个条目，没有定论。
3. **`se_wait` 参数 1 的等待终止条件与时长**。它依赖上面两张表与声音线程
   `0x111xxx` 的状态迁移；没有样本文件就无法给出“等多久”，而这条指令会**阻塞**
   ——按“不阻塞”去实现等于自己编一个时长。
4. **`0x107CB8` 的确切语义**（停/释放哪个声道对象）只到“调用两个声音库入口”为止。

因为第 1、3 条直接决定“播哪个文件、播多久”，本轮**不实现 SE 段**，也不把
`se_req` 映射成任何 `playEffect`：那需要一个未经证明的文件路径，正是禁止的做法。

## 8. 试过但没有定论的路径

- **把组号当卷号**：`0x12D810` 的组 5 确实是“无描述表”，而 `se.afs` 在卷表里
  的 id 也恰好是 5。但 `0x12D810` 的跳表是“描述表指针”分派（组 6/7 复用组 2/1 的
  处理），不是按卷分派，两者相同只是巧合，不能据此把组 5 解释成 `se.afs`。
- **找卷表的引用**：`0x212E00`、`0x212EE0`、`0x212EF8`（`se.afs` 指针）在 ELF 里
  **没有任何 4 字节指针引用**，`0x2e00` 的立即数也只有一处 `-0x2e00` 的无关基址。
  挂载代码不在主 ELF 的可见路径上（或经 IOP 模块），无法把“卷 5”连回指令。
- **`0x12D980` 的另外两个 style**：`style 1/2` 直接取 0，同样只写 staging；
  全盘也没有 `style != 0` 的 `file_read`，无法用它们反推含义。
- **`0x12DA38` 的 style 分支**：`style 1` 走 `0x107D10(0)`（另一套轮询），
  与 `file_read` 的 style 0 不是同一条路，且没有脚本用到。

## 9. 边界与下一步需要的输入

- 本轮**已实现**：`file_read` / `file_wait`（`style 0`、`code 0x50XX`），只记账、
  不生成语句；其它形态一律报 `UnsupportedCommand` 并停止，不静默跳过。
- 本轮**未实现**：`0x224`–`0x234` 的 SE 段。需要下列任一条外部输入才能继续：
  1. **SE bank 的文件名与格式**（哪个文件提供 `0xB1EC88` 的 152/174 项状态表），
     或一份可核对的“编号 → `se.afs` 条目”对照；
  2. 声音线程 `0x111xxx` 中 `se_wait` 终止条件的追出结果，或实机观察
     “这句之后停多久”；
  3. 若两者都无法取得，则只能把 SE 段当作“已知语义、无映射”记录并接受
     时长偏差 —— 这需要使用者明确同意，本轮不擅自这样做。
- 影响面：`MAC_000` 开头仍是 23 句；下一条台词（第 24 句，`0x238`）在 SE 段之后，
  因此“越过 `0x21C`”不等于“多出一句”。
