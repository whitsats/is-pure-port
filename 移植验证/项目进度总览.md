### 2.2 图像：1px 保护边修复（关键历史）

原方案按 32px 步长拼 32×32 tile，导致行尾 tile 被跳过 → 双身体/条纹/白缝。
正确规则（来自仓库提交 `9e2123d` 的技术文档）：

- 像素流按 **1024px 宽的存储行 × 32 行一条带**组织；
- 每个 32×32 tile 有 **1px 保护边**，有效核心 **30×30**；
- 拼图步长 **30px**，且 tile 索引是**全局连续**的（不按部件重置）。

修正后与游戏自带 TIM2 缩略图比对：EV 平均 RGB 差 1.0–1.5，BG ≈1.0–1.7，CHR 3.5–20.4
（旧规则 CHR 为 20.7–48.4）。用户提供的游戏截图中「耳朵凸起 / 太阳穴线条 / 眼镜断裂」问题消失。

### 2.3 TIM2 调色板修正（ETC）

原实现把 CLUT 放在图像数据**之前**、且未对调色板反 swizzle，导致 8bpp 贴图全花。
按参考实现修正：

- `clut_off = pic_header + header_size + image_size`（CLUT 在图像**之后**）；
- 调色板必须反 swizzle：`pos = (p & 231) | ((p & 0x8) << 1) | ((p & 0x10) >> 1)`；
- 调色板可能是 32bit RGBA8（1024B）或 16bit RGBA5551（512B）；
- image_type：3=32bpp、4=4bpp 索引、5=8bpp 索引；alpha 0–128 映射 0–255；
- 加 `viable_pic()` 合法性校验，避免把二进制数据里的假 `TIM2` magic 当成图片（曾因此丢掉 ETC[21] 的全部图）。

修正后可正确读出菜单文字：`Screen Setting / Sound Setting / Message & Font / 修改后可直接读出…`、
`SHORTCUT / OPTION / FILE EDIT / LOAD / SAVE / CG MODE / MOVIE / CONTROL MANUAL`、
角色名牌 `IORI / ITSUKI / IZUMI / AIKO`，以及 TAKARA TOMY、CRIWARE 标识、PS2 手柄图示。

> 该修正只影响带调色板的 TIM2；BG/CHR/EV/BGM 是 32bpp 直读，不受影响。

## 3. MAC 剧本格式（已破解，本次最大成果）

### 3.1 容器与压缩

```
MAC.AFS
├─ 'AFS\0' + 条目数(u32)
├─ 条目表：8B/条（偏移 u32、长度 u32）
├─ 数据区：LZSS 压缩（头部 u32 为解压长度，4096 字节环形缓冲，起点 0xFEE）
└─ 元数据表：meta(u32)/metalen(u32) 指向，48B/条，前 32B 为文件名
```

74 个条目都有名字：`IS01_1.BIP … IS16_3.BIP`、`SCRIPT00–02.BIP`、`STARTUP.BIP`、
`SHORTCUT*.BIP`、`APPEND.BIP`、`DBG_*.BIP`。

### 3.2 单个剧本布局

```
[0 .. text_start)   指令区
[text_start .. EOF) 文本区（连续 cp932 字符串，NUL 结尾；%K=换行 %P=翻页）
```

### 3.3 指令格式

**普通指令 4 字节**：`[op][p1][p2][p3]`

**文本指令 12 字节**（op = 0x60 且 p1=p2=p3=0）：

```
60 00 00 00 | 文本指针(u32) | 行号(u16) | 语音号(u16)
```

- 文本指针 = 剧本内绝对偏移；
- **行号**：每个剧本内从 0 递增，跨 256 进位（低字节正好落在操作码位置）；
- **语音号**：`0xFFFF` = 无语音；否则**直接是 VOICE.AFS 的条目号**
  （实测最大值 **12,789 = 12,790 − 1**，这是决定性证据）。

## 4. 未解决问题

### 4.1 MV(PSS) 音频 —— 旧排查记录（已被本节开头更新取代）

> **历史内容提示：** 本节以下保留修复前的错误产物分析。已查明旧脚本多识别了伪包，且音频需要按 512 字节声道块解交错；「无法解码」「已排除分块重排」及相应的噪声结论不适用于新产物。最新证据和文件见 [MV 音频修复记录](MV音频修复/验证记录.md)。

#### 结论先说

原先交付的 `MV_*_audio.wav` / `MV_*_with_audio.mp4` **是噪声**，判断依据是谱平坦度：

| 音频 | 谱平坦度 | 峰/均值 | 判定 |
|---|---|---|---|
| BGM 音乐（已知正常） | 0.040–0.173 | 84–100 | 正常 |
| VOICE 语音（正常） | 0.297 | 88 | 正常 |
| **MV_OP01** | **0.469** | 27.7 | 噪声 |
| **MV_END01** | **0.465** | 25.6 | 噪声 |
| **MV_LG01** | **0.366** | 48.2 | 噪声 |

> 我最初用的指标是「相邻样本差 / RMS」（0.086–0.138，看起来像音频）——
> **这个指标对低通噪声同样给低值，是无效判据**。教训：音频正确性必须用谱平坦度/听感/与已知正常音频对比。

#### 已确定的字节结构

```
MPEG-PS 私有流 (stream id 0xBD) 的 payload：
[0:17]   封装头：83 80 0a 21 | A A | B B | ff ff ff ff ff ff | a0 00 00
         其中 [4:6]、[6:8] 是两个递增字段（含义未定）
[17:49] 【仅首包】SShd 块：'SShd' + size=0x18 + codec=1 + rate=48000 + ch=2 + block=0x200 + ff×8
[49:57] 【仅首包】SSbd 块头：'SSbd' + body_size = 18,329,600
[57:]   【仅首包】音频数据；后续包从第 17 字节开始就是数据
```

- 0xBD 包共 **4,506 个**（MV_OP01），95.4 s 视频对应 47.2 包/秒 ≈ 每包 21.2 ms ≈ 1018 个立体声帧；
- 包长只有两种：**4090（3418 个）/ 4076（1086 个）**，另有 4061 / 743 / 98 各 1 个（尾部）；
- **异常线索 1（最关键）**：`包长 − 17` = **4073 / 4059，都是奇数** → 每包音频数据不落在样值边界上；
  两种包长差 **14 字节**，成因未明；
- **异常线索 2**：包头 [6:8] 每包递增约 **3810**，而每包样数 ×3.75 ≈ 3817，两者接近但不等，含义未明；
- 数据总量 18,329,600 B ÷ 95.47 s = **192,000 B/s**，精确等于「48kHz × 2ch × 16bit」
  → **体积上必须是未压缩 PCM**（ADX 4bit ≈ 48 KB/s、SPU2 ADPCM ≈ 55 KB/s，都只有 1/4~1/3）。

#### 样值层面的实测现象

- 按 16bit/小端/2ch 解读：**相邻样值相关 0.897、L/R 相关 0.956**（结构上像音频，L≈R 近单声道）；
- 但**自相关无音高周期**（lag1=0.936 平滑衰减，lag24=0.378、lag128=0.348 两个小鼓包），
  波形图呈「有包络的低通噪声」，频谱能量集中在 250–3000 Hz、>8 kHz 仅 3.3%（像电话带宽）；
- 逐 5 秒看：RMS 稳定 6700–10600，谱平坦度全程 0.35–0.58，无一段是正常音乐；
- 开头约 8 秒（0xC00 字节）为全 0 静音，之后才有信号 —— 说明**数据未被整体加密/扰码**。

#### 已排除的假设（都试过）

| 假设 | 结果 |
|---|---|
| 包头长度错（16/17/18/19/20） | **17 字节正确**：相邻样值相关 0.897 / L/R 0.956（16、18 时只有 0.15） |
| 字节序大端 | 更差（谱平坦度 0.86） |
| 平面/分块重排（256/512/1024/2048/4096 B 块） | 最好 0.363，仍不是音乐 |
| 8bit 样值 | 全字节平坦度 0.130（假象），但每 2 字节取 1 就变 0.50 → 只是「两路交织」造成的伪信号 |
| int32 / float32（单/双声道、两种字节序） | 全部 ≥0.45；float32 仅 54% 落在合理数值范围 |
| 多流混淆（把两条音频流拼在一起） | 包率 47.2/s 与 1018 帧/包吻合，是单条流 |
| 包边界不连续（拼接错位） | 拼接处无 >3×RMS 跳变；且包头 17 字节判定一致 |

#### 还没验证的方向（建议下一步）

1. **查 CRI `SShd` 字段定义**：`codec=1 / rate=48000 / ch=2 / block=0x200` 到底各代表什么
   （block=512 可能是「每块 512 字节」或「512 样」）。
2. **解释「包长−17 是奇数」**：如果某类包实际头长是 18 或 20 字节、或包尾有 1–3 字节填充/校验，
   就能解释 4090 与 4076 的 14 字节差；这一步可能直接给出正确拼接方式。
3. **找同引擎/同中间件的 PSS 音频提取参考实现**：
   `PSSound` / `MFAudio` / `Cube Media Player` / `VGSC` 的 PSS demux 源码，
   或 CRI Sofdec SDK 文档里的 "Sofdec Audio" 帧结构。
4. 用**逐帧对齐视频**反推：音频包与视频帧（29.97fps）的对应关系如果是「每帧固定样数」，
   可由视频帧数反推出每包真实样数（2860 帧 vs 4506 包 → 1.575 包/帧，非整数，需要解释）。
5. 注意：**MV_END01 的包长结构与 OP01 相同**（4090/4076 两种），可交叉验证结论。

## 9. 历史教训（避免重犯）

- **不要用「自指涉」的指标验证产物**：相邻样本差、L/R 相关这类指标对错误数据也能给出漂亮结果；
  必须与**游戏自带的东西**（TIM2 缩略图、真实截图、已知正常音频）对比。
- 音频正确性判据：谱平坦度（音乐 <0.2）+ 自相关有音高周期 + 人工听感。
- 解压/解析类脚本改动后要全量重跑并校验**条目数不减少**（ETC[21] 曾因假 TIM2 magic 全部丢失）。
- 宁可不交付，也不交付已知错误产物（本次已删除 3 个 WAV + 3 个带音频 MP4）。
